# City governor (CM) solver: faster, results unchanged (2026-11-01)

Epic `epic/perf4-cm`, based at a9be757fed (tuning HEAD with the perf,
perf-xcallback and perf3 epics merged). Method as in
`perf-turntime-2026-11-01.md` §5-7: profile first, keep the original code
as an oracle, accept only on byte-identity.

**The client shares this code.** `common/aicore/cm.c` is linked into the
server (AI cities through `auto_arrange_workers()` in server/cityturn.c,
`dai_manage_taxes()`, the government evaluation in
`adv_best_government()`) and into the client, where the human's citizen
governor (client/agents/cma_core.c, the sdl cma_fe dialogs) re-solves a
city on every city-info packet. Every per-query speedup below is what a
human with the governor on feels, not just AI turn time.

## 1. Profile (before)

Instruments added for this epic (all off by default):
`FREECIV_CM_STATS=1` (per-turn counts), `FREECIV_CM_BENCH=N` (each query
solved N extra times under a CPU timer: a microbenchmark on the game's
real query mix), `FREECIV_CM_CHECK=1` (oracle, §3).

Per-turn work (FREECIV_CM_STATS):

| turn | queries | B&B loops | bound evaluations | leaves evaluated | repeats* |
|---|---|---|---|---|---|
| late T251 (load turn) | 2,249 | 128,529 | 190,409 | 36,812 | 420 |
| late T252 | 374 | 28,583 | 38,856 | 9,568 | 16 |
| late T253 | 322 | 51,931 | 63,220 | 13,122 | 36 |
| Europe T50 (load turn) | 1,822 | 30,221 | 65,297 | 13,177 | 383 |
| Europe T51-54 | 290-417 | 7.5k-9.0k | 13.4k-16.1k | 3.7k-4.4k | 14-45 |

\* queries whose (approximate) input signature was already seen that
turn; nearly all returned the same result.

The load turn is dominated by government evaluation: in the CM-only
callgrind 76% of the solver's instructions come from
`adv_best_government()` (`cai_gov_value` 52%, `dpai_gov_value` 9%, the
rest its own re-arrangement), i.e. every city re-solved under each
candidate government. Steady turns run ~300-400 queries, 75-160 loops
and ~100-200 bounds per query.

Where a query's time goes (callgrind `--toggle-collect=cm_query_result`,
late save, load turn T251, 2,249 queries, unmodified solver: 14.28 G
instructions):

| piece | Ir | share |
|---|---|---|
| bound (`next_choice` -> `choice_is_promising` -> `compute_max_stats_heuristic`) | 10.96 G | 76.8% |
| - re-deriving the free (centre) tile's output: radius scan x 6 outputs per bound (24.0M `city_map_to_tile`, 1.14M `city_tile_output`, 25.1M `city_tile_index_to_xy`, 24.0M `is_free_worked`) | ~6.7 G | ~47% |
| - `set_city_production` (190k calls; `city_waste` 1.41M calls with 5.25M effect lookups and 57k `nearest_gov_center`) | 2.65 G | 18.5% |
| - `player_content_citizens` per bound | 0.25 G | 1.7% |
| leaf evaluation (`apply_solution` -> `city_refresh_from_main_map`, 38,839 leaves) | 1.87 G | 13.1% |
| initial refresh per query | 0.79 G | 5.5% |
| tile-type lattice (`init_tile_lattice`, `city_tile_output` per tile) | 0.55 G | 3.9% |
| search bookkeeping (`add_workers`, sorting, copies) | ~0.3 G | ~2% |

So the solver was not expensive because of search size (a few hundred
nodes per query) but because each bound recomputed per-search constants.

## 2. What changed (5 commits)

(A first version of commit 4 indexed the waste memo by total; with
negative_ok the partial solutions start at -FC_INFINITY and the bonus
multiplication wraps, so totals reach 10^7-10^9: it grew ~100 MB arrays
and memset them per search -- max RSS 289 MB vs 188 MB. Caught by the
RSS column of the timing pass, replaced by a keyed memo before the
commit was finalised; all identity runs below are on the fixed build.)

1. `common: count cm solver work per turn` -- FREECIV_CM_STATS and
   FREECIV_CM_BENCH.
2. `common: run the cm solver beside its reference on request` --
   FREECIV_CM_CHECK: every query is solved first on the reference path
   (`cm_state.reference`; each helper that gained a faster twin keeps its
   original body there) into a copy of the caller's result, then on the
   default path; any difference in aborted, found_a_valid, disorder,
   happy, radius, surplus[], specialists[] or worker placement is
   log_error()ed. The default path runs last, so the city ends exactly as
   without the check.
3. `common: hoist per-search invariants out of the cm bound` -- the free
   tiles' output and `player_content_citizens()` are computed once per
   search (after the refresh) instead of per bound.
4. `common: memoise city waste within a cm search` -- the bound calls
   `cm_city_production()`, a line-for-line copy of
   `set_city_production()` (same reads and writes, including trade-route
   values) in which `city_waste(pcity, o, total)` is memoised per search
   by total (94% hit rate) and the tithes are looked up once; in check
   mode every bound is also recomputed with the real
   `set_city_production()` and prod[]/waste[] compared.
5. `doc: ...` (this file, STATUS).

### Why each is exact

The search writes only the fields `city_refresh_from_main_map()` and
`set_city_production()` recompute (specialists, citizen_base, prod,
waste, surplus, citizen moods, pollution, trade-route values), and
restores the city struct at the end. With a workers_map the refresh skips
`set_city_bonuses()`, `city_tile_cache_update()` and `city_support()`,
so bonus[], abs_bonus[] and usage[] stay as the initial full refresh set
them.

- Free tile output: `city_tile_output()` reads the tile (terrain,
  extras, resource, roads), `base_city_celebrating()` (size, was_happy)
  and effects with requirement context (owner, city, tile). Every
  city-range requirement reads buildings, size, culture/history,
  anarchy/rapture counters, original owner, acquisition, founding turn,
  famine, counters, goods received or the city's tiles (enumerated from
  `context->city` uses in requirements.c) -- none written by the search.
  Same integers, same sums.
- `player_content_citizens()`: player-range effects and settings only.
- `city_waste()`: size, effects with context (owner, city, output type)
  (same argument), nearest gov center (other cities), settings; writes
  nothing. Pure in (o, total) within a search.
- `cm_city_production()` reads exactly what `set_city_production()`
  reads (citizen_base[] that the bound just set, the constant bonus[],
  abs_bonus[], usage[], owner's rates, partner cities' citizen_base for
  trade routes) and writes the same fields with the same values.

Because every bound returns the same integers, every pruning decision is
the same, so the B&B visits the same nodes in the same order, evaluates
the same leaves, updates `min_luxury` identically, hits the
`CM_MAX_LOOP` abort at the same node, and breaks ties (first strictly
better leaf wins) identically. The per-turn FREECIV_CM_STATS counts
(loops, bounds, leaves, aborted) are equal to the unmodified solver's.

### Not done, and why

- **Tighter bounds (plan option b).** Any bound that prunes more changes
  the visited-node sequence, hence where the 27,500-loop abort lands for
  aborted queries (one in late T253), when `min_luxury` is learned from
  disorder leaves, and which of several equal-fitness leaves is found
  first. Exactness would need a proof for all three; not attempted.
- **Cross-query memo (option c).** Repeats are 4-19% of a turn's queries
  (most on the load/government turn) and an honest signature has to
  cover every input including other cities' tile ownership and trade
  partners; small win, large invalidation surface.
- **Production memo keyed by citizen_base[]** (built, measured, dropped
  before commit): 27% hits, and nearly every late-game city has a trade
  route (233,526 trade-route evaluations in 235,645
  `set_city_production` calls), whose value write made a skip-on-hit
  version inexact for exactly those cities.
- **Lattice from the tile cache.** `init_tile_lattice()` (now 13% of
  what is left) recomputes `city_tile_output()` per tile although the
  initial full refresh just filled `pcity->tile_cache` with the same
  values; `struct tile_cache` is private to common/city.c, so this needs
  a small city.c accessor (out of this epic's scope).

## 4. Speed

Deterministic measure: callgrind with `--toggle-collect=cm_query_result`
(instructions inside the solver only), late save, load turn T251,
2,249 queries, same queries/loops/bounds/leaves in every build:

| build | solver Ir | |
|---|---|---|
| unmodified (`.perf-bin/base`) | 14.28 G | |
| + per-search invariants | 6.54 G | -54% |
| + city waste memo (HEAD) | 4.35 G | -70%, 3.3x |

Per query that is 6.35 M -> 1.93 M instructions.

Microbenchmark, `FREECIV_CM_BENCH=10` (each real query solved 10 extra
times, CPU time; box load 9-11 from another agent's races, so single
numbers swing 1.5x -- read the ratios):

| | unmodified (2 runs) | HEAD (2 runs) |
|---|---|---|
| late T251 (load turn, 2,249 queries) | 1373 / 912 us/query | 533 / 268 us/query |
| late T252 (374 queries) | 1218 / 1474 us/query | 409 / 584 us/query |
| Europe T50 / T51 / T52 | 574 / 637 / 707 us/query | 215 / 212 / 184 us/query |

This is what the client governor feels per re-solve: roughly 3x less
CPU per city refresh.

Game runs, `.perf-bin/base` (unmodified solver, same build options as
HEAD) vs HEAD, back to back, `/usr/bin/time -v`, load 8-10:

| | base | HEAD |
|---|---|---|
| late T251->256: Citizen arrange + Taxes, sum over the run | 4.97 / 4.71 s | 1.96 / 1.54 s |
| - Citizen arrange, load turn | 2.40 / 1.63 s | 0.78 / 0.64 s |
| - Taxes per turn | 0.26 / 0.29 s | 0.11 / 0.09 s |
| late user CPU (pair a: base first; pair b: HEAD first) | 63.5 / 68.6 s | 89.4 / 63.8 s |
| late max RSS | 188.8 / 189.1 MB | 188.8 / 188.6 MB |
| Europe T50->60: Citizen arrange + Taxes, sum | 4.17 s | 1.94 s |
| Europe user CPU | 119.3 s | 122.2 s |
| Europe max RSS | 170.0 MB | 169.7 MB |

The CM buckets drop 2.2-3x, but whole-turn wall/CPU did not separate
from noise on this box: in pair a every AI bucket (pathfinding,
military, workers, none touched here) ran ~1.5x slower in the second
run, and the reversed pair b came out the other way. On steady late
turns CM is a few percent of the turn (~300-400 queries); the saving is
concentrated on government-evaluation turns (the load turn: 2,249
queries, Citizen arrange 2.4 -> 0.8 s) and in the client.

`.perf-bin/ref` (the merged tuning HEAD, built without aitiming and
without -fno-omit-frame-pointer) is the identity reference only; its
timings are not comparable to these builds.

## 5. What is left

After this epic the solver's instructions on the late load turn are
4.35 G (from 14.28 G):

| piece | Ir | share |
|---|---|---|
| leaf evaluation (`city_refresh_from_main_map` with workers_map) | 1.87 G | 43% |
| bound | 0.94 G | 22% |
| initial refresh per query | 0.79 G | 18% |
| `init_tile_lattice` | 0.55 G | 13% |

The rest lives in common/city.c: the leaf refresh re-runs
`set_city_production()` (whose `city_waste()` re-evaluates the waste
effects per leaf) and the happiness chain. A `city_waste()` that took
precomputed effect levels, or a tile-cache accessor for the lattice,
would need common/city.c changes. Government evaluation
(`adv_best_government()`, 76% of load-turn CM work) re-solves every city
per candidate government; that is ai/default/advisors behaviour and
stays as is.
